# 架构与接口

源码路径以同级的 `商城管理系统/` 为根目录。日常启动与关闭见 [项目运行说明](../商城管理系统/README.md)。

2026-10-26 新增库存流水和商品图片，业务例子与操作流程见 [库存管理与商品图片](./库存管理与商品图片.md)。商品新增、编辑不再接收库存字段。

这份文档说明当前代码怎样工作。具体每一行的语法和作用见 [逐行讲解](./逐行讲解.md)。正式前端入口位于 `frontend-vue3/src/`，后端入口为 `MallApplication.java`。

## 1. 前端、后端、数据库的分工

| 部分 | 本项目位置 | 负责的事情 |
| --- | --- | --- |
| 页面 | `frontend-vue3/src/views/` | 展示数据、收集表单草稿、触发查询和保存 |
| 公共组件 | `frontend-vue3/src/components/` | 布局、弹窗、分页、确认与通知 |
| 路由 | `frontend-vue3/src/router.js` | 根据地址显示页面，并做前端登录/角色导航判断 |
| 请求 | `frontend-vue3/src/api.js` | 统一发送 HTTP 请求，处理 JSON、Cookie、CSRF 和失败消息 |
| 会话状态 | `frontend-vue3/src/session.js` | 保存当前用户，恢复登录，执行登录/退出 |
| 控制器 | `backend/src/main/java/com/example/mall/controller/` | 接收 URL、查询参数和 JSON，调用业务服务 |
| 业务服务 | `backend/src/main/java/com/example/mall/service/` | 检查业务规则，划定事务范围 |
| 数据访问 | `backend/src/main/java/com/example/mall/repository/` | 用 JdbcTemplate 执行参数化 SQL |
| 数据结构 | `backend/src/main/java/com/example/mall/model/` | Requests 定义输入及校验；Models 定义返回值 |
| 安全配置 | `backend/src/main/java/com/example/mall/config/` | 密码哈希、会话认证、权限、CSRF 与初始数据 |
| 数据库 | 项目专用 MySQL，或 H2 文件库 | 保存用户、分类、商品、订单与明细 |

一次商品查询的实际调用方向是：

```text
ProductsView.vue 的 load()
  → api.js 的 api('/products?...')
  → 浏览器请求 /api/products
  → Vite 开发代理转发至 127.0.0.1:8081
  → Spring Security 检查当前会话
  → CatalogController.products()
  → CatalogService.products()
  → ProductRepository.findPage()
  → 数据库 SELECT
  ← Page<Product> 转成 JSON
  ← api.js 解析 JSON
  ← products/total/page 的响应式数据更新
  ← Vue 根据模板更新列表与分页
```

`ref`、`reactive` 负责页面状态；持久化来自后端数据库。刷新页面时，前端会重新请求数据，不再把一件无线鼠标固定写成正式商品数组。

## 2. 端口与请求地址

项目启动脚本使用前端地址 `http://127.0.0.1:5174/`，后端只监听 `127.0.0.1:8081`；原来的 5173 练习端口不被强占。前端请求使用 `/api` 相对路径，开发阶段由 Vite 代理到后端。浏览器看到同源请求，无需页面自行拼接后端主机名。

MySQL 本机学习实例使用 `127.0.0.1:3307`，数据库名 `mall_admin`，数据目录为本项目的 `data/mysql/`。脚本把本机随机数据库凭据保存到被 Git 忽略的 `.runtime/mysql.local.json`，文档不记录该密码。H2 作为无需额外数据库进程的备用，默认 JDBC 文件位置相对于后端工作目录为 `backend/data/mall`。

后端 `application.yml` 的基础配置为 H2；项目启动脚本按所选数据库传入 profile 和环境变量。使用 MySQL 时，`application-mysql.yml` 从 `MALL_DB_URL`、`MALL_DB_USER`、`MALL_DB_PASSWORD` 读取连接配置。

## 3. 登录、Cookie 与 CSRF

本项目采用服务器会话认证。

1. 前端通过 `GET /api/auth/csrf` 获取 `{ "token": "..." }`。
2. 登录使用 `POST /api/auth/login`，正文类型为 `application/x-www-form-urlencoded`，字段为 `username`、`password`。
3. 登录写请求同样携带 `X-CSRF-TOKEN`，不能跳过 CSRF。
4. Spring Security 验证用户名、BCrypt 密码哈希和账号启用状态；成功返回用户信息，并使用 `JSESSIONID` Cookie 关联服务器会话。
5. 登录后会话身份变化，前端清除旧令牌，再获取新的 CSRF 令牌。
6. 后续请求使用 `credentials: 'include'` 携带 Cookie。GET/HEAD 以外的请求在请求头添加 `X-CSRF-TOKEN`。
7. 刷新页面调用 `GET /api/auth/me` 恢复当前用户；退出使用 `POST /api/auth/logout`，使会话失效并清除 Cookie，再刷新 CSRF。

`SecurityConfig` 的表单认证过滤器直接处理登录 URL，因此 AuthController 中只需要 `/csrf` 和 `/me` 方法。密码摘要只存在 `mall_user.password_hash` 与认证对象中，不返回前端。

Session Cookie 使用 HttpOnly，前端 JavaScript 不读取它；SameSite 为 Lax，会话超时为 30 分钟。CSRF 令牌用于检查写请求是否来自知道本会话令牌的页面，它不等于用户密码，也不替代登录权限。

`SessionAccountFilter` 在每次已登录请求中重新读取用户。账号停用或密码改变会使旧会话退出；角色改变会更新本次请求权限。前端导航守卫用于调整界面，真正的账号接口权限由后端 `hasRole("ADMIN")` 执行。

| 角色 | 业务权限 |
| --- | --- |
| ADMIN | 概览、分类、商品、库存、图片、订单和账号管理 |
| STAFF | 概览、分类、商品、库存、图片和订单；不能访问账号管理接口 |

初次创建空数据库时，DataInitializer 写入 `admin / Admin@123456`、`staff / Staff@123456`。通过 `app_setting.bootstrap_v1` 记录初始化完成，后续启动不覆盖已有账号密码或业务数据。

## 4. API 清单

除健康检查、CSRF 获取和登录外，以下接口均要求登录；所有写请求还要求有效 CSRF 请求头。用户管理仅 ADMIN 可访问。

| 方法 | 地址 | 输入/返回 | 用途 |
| --- | --- | --- | --- |
| GET | `/api/health` | 返回 application/status | 无需登录，供启动脚本确认商城后端就绪 |
| GET | `/api/auth/csrf` | 返回 `{token}` | 获取当前 CSRF 令牌 |
| POST | `/api/auth/login` | 表单 username/password；返回 User | 登录 |
| GET | `/api/auth/me` | 返回 User | 读取当前登录用户 |
| POST | `/api/auth/logout` | 返回 message | 退出 |
| GET | `/api/dashboard` | 返回 Dashboard | 概览统计、近期订单和低库存商品 |
| GET | `/api/categories` | 返回 Category 数组 | 分类列表 |
| POST | `/api/categories` | CategoryInput；201 Category | 创建分类 |
| PUT | `/api/categories/{id}` | CategoryInput；Category | 修改分类 |
| DELETE | `/api/categories/{id}` | 204 无正文 | 删除无商品引用的分类 |
| GET | `/api/products` | keyword/categoryId/status/page/size；Page<Product> | 搜索、筛选与分页 |
| POST | `/api/products` | ProductInput；201 Product | 创建库存为 0 的商品，可关联已上传图片 |
| PUT | `/api/products/{id}` | ProductInput；Product | 修改资料、图片和上下架；不能改库存 |
| PUT | `/api/products/{id}/status` | `{status}`；Product | 仅修改上下架状态，不把旧列表库存写回 |
| DELETE | `/api/products/{id}` | 204 无正文 | 仅删除没有库存、流水和订单引用的商品 |
| GET | `/api/inventory/movements` | keyword/type/start/end/page/size；Page<StockMovement> | 查询库存流水 |
| POST | `/api/inventory/movements` | StockInput；201 StockMovement | 手动入库、出库并登记流水 |
| POST | `/api/product-images` | multipart file；201 imageUrl | 校验、重新编码、保存图片 |
| GET | `/api/product-images/{filename}` | PNG 图片 | 登录后读取图片 |
| GET | `/api/orders` | keyword/status/page/size；Page<Order> | 订单搜索与分页 |
| POST | `/api/orders` | OrderInput；201 Order | 创建订单并扣库存 |
| GET | `/api/orders/{id}` | 返回 Order | 查看订单及明细 |
| PUT | `/api/orders/{id}/status` | `{status}`；Order | 执行允许的状态流转 |
| GET | `/api/users` | 返回 User 数组 | 管理员查看账号 |
| POST | `/api/users` | CreateUserInput；201 User | 创建账号 |
| PUT | `/api/users/{id}` | UpdateUserInput；User | 更新姓名、角色、状态及可选密码 |
| DELETE | `/api/users/{id}` | 204 无正文 | 停用账号，保留其记录 |

分页从 `page=1` 开始，`size` 允许 1 至 100，默认每页 10 条。统一分页对象：

```json
{
  "items": [],
  "total": 25,
  "page": 1,
  "size": 10
}
```

参数 `keyword` 在商品接口匹配名称/SKU，在订单接口匹配订单号/收货人/电话。SQL 使用 `?` 占位符，参数不直接拼进 SQL 文本；LIKE 搜索还会转义用户输入的 `%`、`_`、`!`，使它们按普通内容搜索。

商品创建/更新正文示例：

```json
{
  "name": "机械键盘",
  "sku": "KEYBOARD-002",
  "categoryId": 1,
  "price": 199.00,
  "imageUrl": "",
  "status": "ON_SALE",
  "description": "商品说明"
}
```

订单创建只提交商品 ID 和数量，价格与总额由后端读取当前商品后计算，前端显示的预估金额不作为订单结算依据：

```json
{
  "customerName": "学习示例收货人",
  "phone": "13800000000",
  "address": "学习示例收货地址",
  "items": [{ "productId": 1, "quantity": 2 }]
}
```

失败响应尽量统一为 `{ "message": "原因" }`。400 表示输入不合法，401 表示未登录/会话失效，403 表示权限或 CSRF 不通过，404 表示记录不存在，409 表示唯一值冲突、库存或状态等业务冲突，500 表示服务内部错误。前端 api.js 对无正文的 204 不执行 JSON 解析，对错误状态提取 message 并抛给页面。

## 5. 数据库表

建表定义位于 `backend/src/main/resources/schema.sql`。`CREATE TABLE IF NOT EXISTS` 不删除已有表；表结构发生变化后需要编写明确的迁移，不能把自动建表当作任意升级工具。

| 表 | 主要字段 | 作用/约束 |
| --- | --- | --- |
| app_setting | setting_key、setting_value | 保存一次性初始数据和库存流水升级标记 |
| mall_user | id、username、display_name、password_hash、role、enabled | username 唯一；保存哈希，账号通过停用控制访问 |
| category | id、name、description | 分类名唯一 |
| product | id、name、sku、category_id、price、stock、status、description、image_url、created_at | SKU 唯一；初始 stock 为 0，商品接口不能改库存；图片保存后端地址 |
| stock_movement | product_id、type、delta、before_stock、after_stock、reference、reason、remark、operator、created_at | 库存流水；商品/类型/关联编号组合唯一，记录每次变化 |
| mall_order | id、order_no、customer_name、phone、address、status、total_amount、created_at | 订单号唯一；总额 DECIMAL(18,2) |
| order_item | id、order_id、product_id、product_name、unit_price、quantity、line_total | 关联订单与商品，保存下单时名称与价格快照 |

关系如下：

```text
category 1 ── N product
mall_order 1 ── N order_item
product 1 ── N order_item
product 1 ── N stock_movement
```

Java 金额使用 BigDecimal。数据库金额使用 DECIMAL，而不是 FLOAT/DOUBLE。商品名称、价格后续变化不会改变已有订单的商品名称、单价和行金额快照。

分类仍有商品时不能删除；商品有非零库存、库存流水或订单引用时不能物理删除，可以下架；账号 DELETE 的业务含义是停用。这样既能阻止继续使用，也保留必要历史记录。

商品上下架使用专用 `/products/{id}/status` 接口。假设列表显示库存 50，但其他人刚下单使库存变成 49，此时点击下架只更新 status，不会把列表里的 50 重新保存到数据库。完整商品编辑同样不接收、不更新 stock，因此编辑名称、价格、图片时也不会覆盖其他业务刚刚更新的库存。

## 6. 订单与库存事务

允许的状态路径：

```text
PENDING 待支付 ──→ PAID 已支付 ──→ SHIPPED 已发货 ──→ COMPLETED 已完成
      │                 │
      └──→ CANCELLED ←───┘
              已取消
```

这里的“已支付”是后台学习用状态标记，未对接第三方支付服务。发货和完成也是后台状态操作，未接物流平台。

创建订单由 `OrderService.create()` 的 `@Transactional` 包住：

1. 检查订单行不能重复提交同一商品 ID。
2. 按商品 ID 排序，以一致顺序加锁，降低多个订单互相等待造成死锁的机会。
3. `SELECT ... FOR UPDATE` 锁定对应商品行。
4. 检查商品仍上架、库存足够。
5. 调用 InventoryService，在相同事务中用条件 UPDATE 检查新库存范围并扣减，要求影响行数为 1，同时登记 ORDER_DEDUCT 流水。
6. 从商品读取名称/价格快照，用 BigDecimal 计算行金额和总额。
7. 插入订单与所有明细。
8. 任一步骤抛出运行时异常，整笔事务回滚，已经扣掉的库存和新增的流水一起撤销。

状态修改由 `OrderService.changeStatus()` 包住事务：先锁订单，检查当前状态能否流向目标状态；取消时按商品 ID 顺序锁商品并归还库存；最后更新订单状态。已取消订单没有继续流转路径，因此重复取消会被拒绝，库存只归还一次。已发货不能取消，已完成不能再修改状态。

## 7. 表单草稿、取消与请求竞态

各页面用 draft 保存表单副本。点击编辑时复制商品等字段，不把输入框直接绑定到列表对象；点击取消只关闭表单，尚未提交的文字不会写入数据库。保存成功后再重新查询列表，保证展示的是后端保存结果。

列表查询使用递增 requestId，只接受最后一次发起的请求结果，避免用户快速搜索时旧响应覆盖新查询。saving/acting 用于防止正在提交时重复操作。删除当前分页最后一条记录时，页面会退回上一页继续查询。

## 8. 推荐阅读顺序

先从 `index.html → main.js → App.vue → router.js` 认识入口；再读 `LoginView.vue → session.js → api.js → SecurityConfig → AuthController` 理解登录；然后跟随 `ProductsView.vue → CatalogController → CatalogService → ProductRepository → schema.sql` 理解商品；最后读订单事务和管理员保护规则。

逐行文档给出每个手写运行文件的对应代码与解释。阅读时一次沿一条请求路径走通，比同时记住所有类名更容易理解。
