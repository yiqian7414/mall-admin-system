# 库存管理与商品图片（2026-10-26）

这次改动以“库存只能通过出入库业务变更”为规则。新增商品时不填写库存，后端固定创建为 0；编辑商品只改资料、图片和上下架状态，不改库存。

## 一、怎么使用

1. 在“商品管理”点击“新增商品”，填写名称、SKU、分类、售价，可选择一张商品图片。
2. 保存商品。默认状态为下架，库存为 0。
3. 到“库存管理”点击“商品入库”，查找商品，填写入库数量、原因和备注。
4. 确认入库后，库存增加，系统同时保存流水。在“库存总览”可以查看当前数量。
5. 回到商品管理，将准备销售的商品上架。
6. 商品报损、内部领用等情况，到库存管理办理“手动出库”。不要为已经由订单扣减的商品再办一次出库。

入库和出库的“数量”均填写正整数。比如出库 3 件填 3；流水中自动显示 -3。商品状态为下架时仍然可以办理出入库。

## 二、算一个完整例子

| 业务 | 本次数量变化 | 变动前 | 变动后 |
| --- | ---: | ---: | ---: |
| 新建商品 | 不产生库存 | — | 0 |
| 采购入库 20 件 | +20 | 0 | 20 |
| 创建购买 3 件的订单 | -3 | 20 | 17 |
| 报损出库 2 件 | -2 | 17 | 15 |
| 取消刚才那笔订单 | +3 | 15 | 18 |

当前项目的 stock 代表用于订单分配的数量，没有把仓库实物数量与订单占用数量分开保存。订单创建就扣减；付款、发货和完成时不再扣减。订单取消会归还数量，但已发货或已完成的订单仍然不能直接取消。

“库存总览”像银行卡余额，显示现在有多少；“出入库记录”像流水，显示每次为什么变化。订单扣减不代表货物已经离开仓库，因此流水明确区分“订单扣减”与“手动出库”。

## 三、为什么不能只删掉库存输入框

页面没有输入框，只能防止正常操作时填写库存。别人还可能直接请求后台接口，所以后端也必须限制。

ProductInput 已经没有 stock 字段，且项目启用 fail-on-unknown-properties。向商品新增、编辑接口额外发送 stock 会返回 400；商品新增 SQL 直接写入 0，商品编辑 SQL 的 SET 列表也没有 stock。

例如这段旧请求现在会失败：

```json
{"name":"鼠标","sku":"MOUSE-NEW","categoryId":1,"price":59,"status":"OFF_SALE","stock":999}
```

正确商品请求可以包含 name、sku、categoryId、price、status、description、imageUrl，但不能包含 stock。

## 四、一次手动入库经过哪些代码

```text
InventoryView.vue：收集商品、数量、原因和备注
  → api.js：带 Cookie 和 CSRF 令牌发送请求
  → InventoryController：校验 StockInput 请求
  → InventoryService.manual：检查业务原因，生成带方向的数量
  → InventoryService.move：锁定商品、核对是否已处理、检查数量范围
  → ProductRepository.adjustStock：数据库加减库存
  → StockRepository.insert：记录变动前、变动后、业务、单号、操作人和时间
  → 事务提交后，页面重新查询最新结果
```

这些数据库操作在同一个事务里。写流水失败时，库存修改也会回滚；多商品订单的某项失败时，整个订单中的库存和流水一起回滚。

假设只剩 1 件，两名员工同时各出库 1 件，行锁让两次操作依次检查，只有第一次成功，第二次会收到库存不足。数量不会减成负数。变更后的库存上限为 10 亿。

## 五、为什么刷新或重复点击不会重复入库

每次打开出入库表单，前端生成一个 requestId。同一次提交重试仍使用这个编号。服务端在商品行锁内检查相同商品、业务类型和编号是否已经存在：相同内容直接返回原流水；更改数量或原因却沿用旧编号则拒绝。

这里的设计防止“同一请求重试”重复执行，不会把两次分别打开表单的真实入库合并。

## 六、图片上传怎么保存

1. 选择图片后，浏览器先用临时预览地址展示，还没有保存到数据库。
2. 点击保存商品时，前端使用 FormData 上传文件；浏览器负责补全 multipart 边界，api.js 不手动设置它的 Content-Type。
3. 后端解析实际图片内容，允许 JPG、PNG、WebP；不单凭文件名或 MIME 判断。
4. 原文件不超过 5 MB，宽高各不超过 4096 像素。图片重新编码为 PNG 后保存，统一移除原文件中的附加内容；仅保留第一帧。
5. 后端使用随机 UUID 命名，商品表保存后端返回的 imageUrl。
6. 商品列表和编辑弹窗用这个地址展示图片。没有图片或加载失败时，列表退回文字缩略图。

默认图片目录相对于后端工作目录为 `backend/data/uploads/products/`，不是临时预览地址。重新启动不会自动删除图片。图片接口要求登录，不能把这个本机地址当作对外公开的商品图床。

移除商品图片会清除商品对图片的引用；为避免误删其他引用或丢失旧图，当前不会自动删除磁盘文件。取消商品表单也可能留下已经上传但未引用的文件，后续如需清理应单独设计并确认范围。

迁移项目时需要同时带上数据库和上传目录。Git 忽略 data，意味着 GitHub 不会自动保存本机上传图片；正式备份不能只靠源码仓库。

## 七、旧数据如何处理

InventoryMigration 先检查商品表是否已有 image_url，缺失时只追加该列，不重建商品表。

OpeningInventory 在第一次启用流水时，为没有流水的旧商品记录“升级期初库存”。例如原来库存为 37，升级后仍为 37，只增加一条基线记录。它不伪造历史采购明细，之后重启也不会重复登记。

新建空数据库的演示商品同样先以 0 创建，再经过库存业务办理初始演示入库。

已有库存、库存流水或订单引用的商品不能直接删除，应使用下架保留记录。流水当前只读，没有修改、删除入口。发生录错时可以办理一笔相反方向的手动业务，并在备注中注明原流水编号，保留修正痕迹。

## 八、新增接口

所有接口均需登录；写请求还需有效的 X-CSRF-TOKEN。管理员和员工都可办理库存业务及上传商品图片。

| 方法 | 接口 | 作用 |
| --- | --- | --- |
| GET | `/api/inventory/movements` | keyword/type/start/end/page/size 查询流水 |
| POST | `/api/inventory/movements` | 手动入库或出库 |
| POST | `/api/product-images` | multipart 的 file 字段上传图片 |
| GET | `/api/product-images/{filename}` | 登录后读取保存的图片 |

手动库存请求例子：

```json
{
  "productId": 1,
  "type": "INBOUND",
  "quantity": 20,
  "reason": "采购补货",
  "remark": "新到货",
  "requestId": "a0d34c18-9809-42ee-8d28-726e430d7bb3"
}
```

手动类型仅允许 INBOUND、OUTBOUND；ORDER_DEDUCT、ORDER_RETURN 由订单服务生成，OPENING 由升级程序生成，不能从手动接口伪造这些业务类型。

入库原因：采购补货、其他入库。出库原因：商品报损、内部领用、其他出库。

## 九、主要文件与学习顺序

先看页面，再跟随请求阅读后端，最后理解锁和事务：

- `frontend-vue3/src/views/InventoryView.vue`：库存总览、流水、筛选、出入库表单与计算预览。
- `frontend-vue3/src/views/ProductsView.vue`：取消库存输入、图片选择、上传与商品保存。

- `backend/src/main/java/com/example/mall/controller/InventoryController.java`：库存接口入口。
- `backend/src/main/java/com/example/mall/service/InventoryService.java`：库存规则、幂等、行锁和事务。
- `backend/src/main/java/com/example/mall/repository/StockRepository.java`：库存流水 SQL。
- `backend/src/main/java/com/example/mall/service/OrderService.java`：订单统一调用库存业务。
- `backend/src/main/java/com/example/mall/service/ProductImageService.java`：图片校验、重新编码和文件保存。
- `backend/src/main/java/com/example/mall/config/InventoryMigration.java` 与 `OpeningInventory.java`：旧库升级。
